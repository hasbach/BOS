# Security review — M0 Platform Foundation (T089)

**Date**: 2026-11-12
**Scope**: constitution (Principles I, VI, VIII), spec FR-003–FR-011, FR-016–FR-020a, FR-025,
FR-032–FR-035, SC-003/004/005/007, research R4–R7, R13, R14, R17, R21–R27, R30, R33; the
backend (`backend/app/**`, migration `0001_platform_foundation.py`) and the frontend's
security-relevant parts (`src/lib/api.ts`, `next.config.ts`, `src/proxy.ts`,
`src/lib/fragment.ts`, `public/sw.js`).
**Method**: code reading against the spec, greps over logging and error paths, the existing
test suites, new tests for every fix and for claims not yet covered
(`backend/tests/integration/test_security_review.py`), dependency audits, git-history scan.
The current `.env` was not opened; only its ignore status and history were checked.

## Findings

| ID | Severity | Status | Finding | Recommendation / change |
|---|---|---|---|---|
| F-01 | **High** | **Fixed (needs config)** | `client_ip()` used `request.remote_addr`. The browser reaches the API only through the web app's rewrite (and in production a reverse proxy), so every request had the proxy's address: the 30-failures-per-address limit counted **all users together** — 30 bad passwords from anyone in 15 minutes would lock every sign-in on the platform — and history/sessions recorded the proxy's IP. | Added `BOS_TRUSTED_PROXY_HOPS` (0–5, default 0): when set, Werkzeug `ProxyFix(x_for=n, x_proto=n)` wraps the app (`app/__init__.py`, `app/config.py`). `.env.example` now sets `BOS_TRUSTED_PROXY_HOPS=1` with an explanation. **Action needed**: add `BOS_TRUSTED_PROXY_HOPS=1` to the local `.env` and every deployed environment (done for the local `.env`, and the local API on 5100 restarted with it); the API must then never be reachable directly by clients, or they could forge `X-Forwarded-For`. Tests: `test_behind_a_trusted_proxy_the_client_address_is_counted`, `test_trusted_proxy_hops_must_be_a_small_number` |
| F-02 | Medium | **Fixed** | API responses had no `Cache-Control`. Responses carrying one-time links (invitation/activation/reset) and personal data could be kept by the browser cache or an intermediary; no `nosniff` on JSON. | Every response now gets `Cache-Control: no-store` (unless the view sets one, as the logo does) and `X-Content-Type-Options: nosniff` (`app/__init__.py`). Test: `test_api_answers_are_never_cached_and_never_sniffed` |
| F-03 | Medium | **Fixed** (T087) | The web app sent no security headers: sign-in, password and employee screens could be framed by another site (clickjacking); no `nosniff` / `Referrer-Policy`. | `frontend/next.config.ts` now sends `Content-Security-Policy: frame-ancestors 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` and `Permissions-Policy: camera=(), microphone=(), geolocation=()` on every route (test `tests/security-headers.test.ts`; checked on the e2e server). Proxied `/api/v1` answers keep the API's own headers (F-02). A full script CSP needs Next.js nonces and is a separate task; HSTS belongs on the TLS proxy at staging |
| F-04 | Medium | **Open (known)** | Password-reset request timing: for an active user's email the request does a tenant transaction (invalidate old links, insert, history), renders the template and sends SMTP **inline** (up to the 10 s SMTP timeout), then a second transaction for `email.sent`; for an unknown email it returns right after the rate-limit insert (`accounts.py:298-336`). The 204 body is identical, but the response time reveals whether an email is registered (FR-007 intent). Rate limit (3/address/hour) slows probing of one address but not of many addresses; there is no per-IP limit on reset requests, so it can also be used to send reset mail to many addresses. | Fix with the M1 job queue: enqueue (or do nothing) and answer immediately in both cases. Interim option without a queue: do the lookup/issue/send in `response.call_on_close` (needs its own app context) so both answers return after the same work (the rate-limit transaction). Add a per-IP limit on reset requests (e.g. 10/IP/hour, reusing `login_attempts`) |
| F-05 | Low | **Fixed** | `flask bos create-operator` on an existing operator set a new password but left that operator's sessions alive (up to 7 days) — after a leaked operator password the old session kept working. | The command now revokes the operator's live sessions when it changes a password and says how many (`app/cli.py`). Test: `test_resetting_an_operator_password_ends_their_sessions` |
| F-06 | Low | **Fixed** | `Config`'s dataclass repr included `secret_key` and the database URLs with passwords; any printed/logged config or a pytest failure showing the `config` fixture exposed them (observed during this review in local test output, not in any committed file). | `field(repr=False)` on those three fields (`smtp_password` already had it). Test: `test_config_repr_holds_no_secret`. Consider rotating the local `BOS_SECRET_KEY` and app DB password if test output was shared |
| F-07 | Low | **Fixed / residual open** | SQLAlchemy errors embed bound parameters (`[parameters: …]`), and `log.exception` in `errors.py` / `request_context._after` logs them: password hashes, token hashes, emails, phone numbers could reach logs on an unexpected database error. | Engine `hide_parameters=True` (`app/core/db.py`). Residual: PostgreSQL's own message/DETAIL still quotes values for type errors and duplicate keys (e.g. `Key (email)=(…) already exists`); expected duplicates are caught and mapped, so this only appears for unexpected errors. Accept, or strip `DETAIL` in the unhandled-error logger later |
| F-08 | Medium | **Open (deployment)** | No production serving design yet: `backend/Dockerfile` runs `flask run` (Werkzeug development server) and `docker-compose.yml` runs it with `--debug` (Werkzeug debugger; the API has no published port, so dev-only exposure). No TLS proxy config exists (T008 deferred to staging). | Before staging: serve with a production WSGI server (e.g. gunicorn) behind the TLS proxy, never `--debug` outside development; set `BOS_COOKIE_SECURE=true` (the default), `BOS_TRUSTED_PROXY_HOPS` (F-01), HSTS and the headers of F-03 at the proxy |
| F-09 | Low | **Open — product decision** | Invitation acceptance answers `identifier_unavailable` when the contact belongs to a user of any business. The inviter holds the link, so an owner/manager can learn whether a phone/email is registered in BOS by inviting it and opening the link (each probe leaves `invitation.created` in their own history; nothing about *which* business leaks). This follows FR-012a/R22 as written. | Product owner to confirm the residual oracle is acceptable for M0 (it is inherent to platform-unique identifiers without verification), or require verification of the contact before acceptance once BOS can send SMS/email |
| F-10 | Low | **Open** | `npm audit`: 9 moderate advisories, all in the `typescript-eslint` / `@typescript-eslint/*` chain (`<=8.72.2`), dev-only lint tooling, not shipped. Production dependencies: 0. Python: 0. | Update `eslint-config-next` / `typescript-eslint` within the current major when a fixed version is available; do not `npm audit fix --force` |
| F-11 | Low | **Open** | Production-safety of configuration relies on discipline: `BOS_SECRET_KEY` (also the HMAC key for rate-limit hashes) is not checked for length or the `CHANGE_ME` placeholder; `.env.example` (a dev template) sets `BOS_COOKIE_SECURE=false` and `BOS_ALLOW_DEMO_SEED=true`. | Refuse to start (outside testing) when the secret is shorter than 32 characters or starts with `CHANGE_ME`; keep a separate production env template without the dev values |
| F-12 | Low | **Open** | Reset emails go over SMTP without STARTTLS when `BOS_SMTP_USER` is empty (`mailer.py` `_deliver`): fine for local Mailpit, but a production relay without auth would carry reset links in clear. | Add `BOS_SMTP_STARTTLS` (default on outside development) or require TLS whenever the host is not local |
| F-13 | Info | Open | Signing in again in a browser that already holds a live session (e.g. another user on a shared phone) replaces the cookie but leaves the old session live server-side until it expires; it is listed under that user's devices and can be ended there. Not session fixation. | Optionally revoke the session named by the incoming cookie at sign-in |
| F-14 | Info | Accepted (design) | `operators`, `sessions`, `login_attempts` are not under RLS (R23); the app role can read operator password hashes and all sessions' token hashes. All queries are narrowed by token hash or owner id (`app/core/sessions.py` docstring). | None for M0; revisit if operators get more power |
| F-15 | Low | **Open** | The common-password list has 18 entries; FR-010/R4 intend a check against a list of common passwords. | Ship a larger list (e.g. the 10,000 most common passwords filtered to ≥10 characters) as a data file |
| F-16 | Low | **Fixed** | Exit-gate P2. `PATCH /staff/{id}` and `PATCH /stores/{id}` checked the request body before looking the record up, so an invalid body was answered 400 and left **no** `access.denied_tenant` entry even for another business's id, while a valid body got 404 and an entry: the order of checks differed with the body. Tests (`tests/isolation/test_uniform_answers.py`, 58): `test_foreign_and_made_up_ids_get_one_answer_whatever_the_body` (26 route/body variants x owner, manager: same status and body, entry per request), `test_the_password_reset_of_every_foreign_staff_id_is_recorded`, `test_an_invalid_body_for_the_callers_own_record_is_still_a_validation_error`, `test_every_business_route_with_an_id_in_its_path_is_in_the_list_above` (a new id route must be added to the list) |

## Changes made by this review

- `backend/app/__init__.py` — optional `ProxyFix` (F-01); `Cache-Control: no-store` and `nosniff` on every response (F-02).
- `backend/app/config.py` — `trusted_proxy_hops` from `BOS_TRUSTED_PROXY_HOPS` (validated 0–5); secrets out of `repr` (F-06).

- `backend/app/cli.py` — `create-operator` ends the operator's sessions when it changes the password (F-05).

- `.env.example` — `BOS_TRUSTED_PROXY_HOPS=1` with explanation.
- Not changed: `frontend/` (F-03 described above), README, the migration.
