## 1 — Catalog (T057; SC-001, SC-004, SC-007)

1. Owner → More → Catalog → Add product. Start the timer as the form opens; stop when save has succeeded and the new product is shown, not when Save is tapped. Enter `JN-TEST`, `Test jeans` / `جينز تجريبي`, Size 30/32/34, Colour Blue/Black, 45 USD for all, `٥` as each opening quantity, two photos and Store A only. Record elapsed time separately for `en` and `ar` (must be <180 s each), product and variant IDs, the actual SKUs, labelled approximate LBP and the 5/0/5 on hand/reserved/available values for six variants.
2. On `JN-TEST2`, enter a lower-case, space-padded copy of the saved `JN-TEST-32-BLUE`. Expect field-level `sku_in_use` naming Test jeans. Create that SKU as the Second Shop owner and expect success. On a new form, attempt the oversized photo and renamed PDF; verify field errors, retained draft, Save blocked until the refused photos are removed.
3. As Store A sales, search `test`, `jn-te`, `32-BLU`; verify the product, photo, variants, price and available. As Store B sales, search and open the copied product URL directly; expect no search hit and not found. Verify the owner's History contains `access.denied_store` for the direct request.
4. As packing, open product and verify no Edit/Adjust. Submit `PUT /api/v1/catalog/products/<id>` in that session with the CSRF header and an edit body (copy the owner's actual form request shape, not their session headers). Expect 403; owner verifies `access.denied_permission`, and product is unchanged.
5. Open the same edit version as owner and manager; make distinguishable edits, save owner then manager. Expect stale `product_changed` with the current version shown. Verify Delete is unavailable because of opening stock; archive and retry Store A search, consult owner's Archived filter and retry a taken SKU on a fresh form. Expect hidden from staff, visible to owner, and SKU still held.

## 2 — Stock adjustments (T070; SC-002, SC-007)

1. Use a fresh active variant, 10 on hand and zero reserved. As manager, Add → Received → 5; capture preview at 15/15 and confirm saved 15. Remove → Damaged → 1; Set count → 12. Check movement −2 with counted 12; timestamp/person/reason, running balances and signed sum 12 across history (four rows if starting with a single opening movement).
2. Open two sheets at the same version; save a +1 in the first, submit the second and capture updated numbers and refusal before retrying knowingly. Verify Remove 20 cannot save and does not change the ledger. Then double-tap a valid Save and show one new movement. A lost-response replay is backend evidence, not a manual result.
3. As owner verify `stock.adjusted` with before/after; as packing send `POST /api/v1/catalog/variants/<id>/adjustments` with `{"reason":"received","quantity":1,"balance_version":<integer>}` and the headers above. Expect 403, no new movement, and a matching `access.denied_permission` in owner's History.

## 4 — Low-stock warnings (T088)

1. Owner → More → Settings: record low-stock default 2 on a fresh business (do not silently overwrite changed data). Use an active variant with available 5; set per-variant level 3, record damaged −2, verify the Low chip on both variant and product. From Sales → low-stock row and from Catalog → Low stock, verify variant/product names, available 3, on hand and threshold 3. Keep or create an active out-of-stock fixture with a nonzero threshold and check it precedes the Low row.
2. Record received +4 on the first variant: it leaves the list. Set a different active variant's threshold to 0 and take available to 0: appears as Out on the product, not in Low stock. Use/retain a separate qualifying Low product for the sales check so both chips can be observed.
3. As Store A agent, see applicable Low/Out chips and the Low filter, but no list link. Direct `GET /api/v1/catalog/low-stock` returns 403; owner checks matching History refusal.

## 5 — CSV import (T102; SC-005)

1. Owner → Catalog → Import CSV → download template. Open in spreadsheet, verify Arabic text/rendering and one example product (two variant rows), then save UTF-8 CSV. Use unique codes/SKUs and Arabic content. Prepare 40 valid rows plus three distinct rows: one repeats a SKU, one omits price, one has negative opening quantity. Use otherwise valid cells; count header as row 1. Record the three expected row numbers and capture pre-import Catalog baseline.
2. Upload; capture exactly the three localized row/column/reason errors, confirm unavailable, baseline unchanged. Fix all three rows, save UTF-8, re-upload; compare product, variant and opening-unit counts to sums from the file. Confirm; verify all products in Catalog, history shows the `opening` movement for nonzero opening quantities, and exactly one `catalog.imported` in owner History. Keep this shop's committed batch ID for scenario 6.
3. Re-upload the same fixed file; all data rows report SKU or code in use and no products are added. Verify imported products appear under No photo. Separately upload a CSV with `image_url`, a 3 MB CSV, and a binary `.xlsx` (rename it to `.csv` too if the picker filters extensions); verify one file-level refusal for each before row validation. Do not use this hand-run CSV for the separate backend 500-row preview timing.

## 6 — Isolation between businesses (FR-030, SC-007)

1. As the Denim House owner, capture known-valid product, variant, photo and committed or previewed import batch IDs (record identifiers, not session credentials). As the Second Shop owner in a separate session, GET `/api/v1/catalog/products/<product-id>`, `/api/v1/catalog/variants/<variant-id>/movements`, `/api/v1/catalog/photos/<photo-id>/thumb`, `/api/v1/catalog/imports/<batch-id>`. For each compare to the corresponding request with a well-formed random nonexistent UUID, using the same session and comparing status and public error code/body apart from per-request metadata. Expect indistinguishable 404s; also check localized not-found UI where it exists.
2. Inspect Second Shop owner's History for `access.denied_tenant` attributable to those requests; compare Denim House History before and after and verify no corresponding event in the source business. Do not use a role lacking the route's permission, which would test a different guard.
