# T107 mobile browser checks

Run separately from the normal e2e suite; this config does not start, reuse, seed, or clean up any servers or databases. Use one worker, no retries, and do not build or run other suites during sampling.

1. Provision a fresh loopback PostgreSQL database named `bos_t107_` followed by 12 lowercase hex digits. Verify both the migration and app connections point to it, not dev or `bos_test`; set explicit connection URLs, temporary uploads and mail outbox, and a generated `BOS_DEMO_PASSWORD`. Migrate through `0003` and run `flask bos seed-demo` in that environment. Run `flask bos seed-catalog --variants 5000 --tenant 20099d26-9d74-5fd1-b2e3-c9a846f4a731` (Demo Second Shop); verify exactly 1,000 products and 5,000 variants there. In that tenant's app-role transaction add a translated name for the Arabic search case (`UPDATE products SET name_ar = 'جينز الأداء ' || split_part(name_en, ' ', 3) WHERE name_en LIKE 'Performance Denim %'`); verify 1,000 updated rows, then `ANALYZE`. Leave the other demo tenant's stock fixtures intact.
2. Start the isolated Flask API on `127.0.0.1:5197` with public base URL `http://127.0.0.1:3217`. On Node 24, start `node e2e/api-relay.mjs 5187 5197` from `frontend/`. In a temporary copy of `frontend/`, build then serve Next.js with `BOS_NEXT_DIST_DIR=.next-t107` and `BOS_API_INTERNAL_URL=http://127.0.0.1:5187`, binding `next start -H 127.0.0.1 -p 3217`. Verify the isolated stack responds before sampling.
3. From the repository's `frontend/` with Node 24, set `BOS_T107_ORIGIN=http://127.0.0.1:3217`, `BOS_T107_DB` to the verified disposable database name, and `BOS_T107_PASSWORD` to its generated demo password. Run `node node_modules/@playwright/test/cli.js test -c performance/playwright.config.ts --output <temp-results>`; use `--project=ar -g 'stock history$'` to run just one case, or `--repeat-each=3` for repeated samples. `T107` JSON lines record completed samples; an assertion/timeout without a timing line is not a measured budget miss or a pass.
4. Stop only the isolated servers, drop the disposable database, and verify its absence.

The checks apply the M0 profile's target RTT, bandwidth and CPU slowdown to the live browser via CDP. They measure readiness against real content, not Lighthouse Lantern LCP. Navigation checks start at navigation start; sheet/import interaction checks start at the captured browser event. Search starts at input, includes the debounce, and ends after the matching row becomes visible and the browser has a rendering opportunity. CSV timings use a one-row input; the 500-row integration budget is separate. See [T107 timing boundaries and action evidence](../../docs/performance.md) for the cold chooser check, interaction-only setup, and what an unmeasured failure means.

Set `BOS_T107_PROFILE=1` for `T107_PROFILE` JSON alongside the unchanged readiness assertions. Times in the profile are relative to navigation start; subtract `trigger` for interaction phases. `nav` and `assets` show document, bundle, CSS, and font requests; `api` shows browser request timing. Join the API `id` to the Flask `bos.request request_id=… ms=…` log to separate server processing from browser wait and body transfer. The first data fetch on client-loaded routes is a marker for when the effect could run, not a direct React hydration measurement. Long tasks, resource downloads, and RSC fetches may overlap; do not add their totals. The profile includes resource entries observable at collection time, not a complete trace of requests still in flight.
